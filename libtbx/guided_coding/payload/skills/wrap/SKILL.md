# /wrap — close out the current change

Run only when the developer invokes it. Do these in order and report each:

1. **Change record complete.** Open the change's file in `.claude/records/`. Every section of the template is filled or explicitly marked not applicable: plan as approved, baseline/candidate/pinned-test identities, every verification command with context and outcome, review findings and dispositions, the pre-integration recheck, the developer's decision, the integration result, limitations.
2. **Tree state.** `git status --porcelain` on the live tree; report it. It must match what the developer expects (restored state plus the integrated change, nothing else).
3. **Worktrees and scratch copies.** After the preservation tags (housekeeping section below) are confirmed, remove THIS change's own construction worktrees, scratch worktrees and branches (DECISIONS.md: your own housekeeping) and list what was removed; anything belonging to the developer or to another change is listed and left alone.
4. **Procedure integrity.** From the repository top, `shasum -a 256 -c .claude/MANIFEST.sha256`; report any line that is not OK.
5. **What remains.** State any open finding held for a later stage, any deferred repair, and the next action if there is one.

**LIGHT-PATH closeout (read this paragraph only, then skip to the housekeeping section):** there is no proof packet. Name the evidence archive instead - its path, its hash, and what it holds: the record, the diff, the check's evidence (run logs with exit statuses, or the inspection record), the commit id, the checksum list - say that the change is integrated locally and will be published inside a publication batch, then go to the housekeeping. Nothing in the FULL-PATH paragraph applies.

**FULL-PATH closeout:** for every outcome that produced a candidate, name the proof packet and how to read it, without being asked - starting with `PROOF_SUMMARY.md`, which every packet carries as its first file and which answers, in plain words: what was wrong, what was done, what changed, what was tested, what the results were, and whether the job is complete: its full path, its identity hash, what to open first, and the companion files that sit OUTSIDE it by design (the approvals record, the live change record). A developer should never have to ask where the proof is.

Deliver the packet as a FILE, not only a directory: a single archive named for the change and revision, placed in the developer's Downloads folder, with its own SHA-256 stated - built with `COPYFILE_DISABLE=1` so no macOS metadata (`._*`) enters it, its member list checked for such names before the hash is reported, and the change's approvals record placed BESIDE the frozen packet archive inside the bundle (the Helper reads the packet, the checker's sheet and the developer's decisions together; a bundle without the approvals record is incomplete) - a directory cannot be attached to a bug ticket. Beside it write TICKET_SUMMARY.md: the bug, the fix, the test, the evidence in plain words, the published commit, any open item stated plainly, and the full packet's location and hash for anything the archive leaves out. That file is what the developer pastes into the ticket; the archive is what they attach.

When the archive is slimmer than the packet, the rule is what is needed to PROVE and nothing else. In: the record, the approved plan, every diff including repair diffs, the test in both forms, the hash manifest, the completed checklist, the approvals record, the decisive-run output, EVERY regression round including the final one run against the shipped bytes, the suite rosters and their comparison, the restoration verification, the cross-repository search, the starting tree state, and the list of tests selected. Out: the procedure documents themselves and the harness's own scripts and console logs. Then CHECK IT: every file cited by a completed checklist line must be present in the archive, and say so - a slim package whose omissions were not verified is not a proof.

Then, when there is a candidate, paste the artifacts themselves - the integrated diff in full (fenced), and the test's decisive assertions (the full test in the review packet for the Guide when long). For a NO CANDIDATE outcome there is no packet, no diff and no test: the record is the deliverable, and /wrap says so in one sentence instead: the developer sees the thing, not a description of it. Then, nearly last on the page and clearly set off, a closing summary in three short plain paragraphs a reader with no context can follow - **The bug** (what failed, for whom, why), **The fix** (what changed, in words, with the file named), **The test** (what it checks and where it lives). No procedure vocabulary in it.

For a PUBLISHED outcome, /wrap quotes the approval pipeline of the workflow's stage 8 (the proof packet) - frozen packet, checker signatures, Helper approval or recorded waiver, Developer authorization, with the packet identity hash; publication without them is a defect. For every other outcome (saved locally, discarded, not reproduced / stopped) the pipeline is not required and is not invented; the closeout says which outcome this is.

Every outcome owes the same housekeeping - a DISCARDED change no less than a published one: preservation tags for every commit the record cites that master does not contain (including dangling stash commits, which no ref holds and garbage collection will take), then the subagent copies and their branches removed, then the pre-harvest check returning nothing. Housekeeping left undone by an abandoned change silently forbids the test suite for everyone who follows. Report the same three timing figures the workflow names, each **labelled by its source**: elapsed (measured), machine working (measured), and time waiting for the developer - the prompt-displayed-to-answered gaps (measured). Do not report the developer's attention minutes: no instrument can observe whether the developer was reading, thinking, working elsewhere or away, and they are never asked for.

Set the record's generated Status section's first line to `- Status: CLOSED` and rewrite `HANDOFF.json` with `open_change.status` "closed". Closeout depends on the ACTUAL outcome, and says which it is: PUBLISHED (the gate satisfied; quote the approvals and packet hash); SAVED LOCALLY (integrated on local master, publication deferred - say exactly what remains before publishing); DISCARDED (what was tried, why discarded, what evidence is preserved); NOT REPRODUCED / STOPPED (the legitimate non-patch closeouts - the diagnostic packet is the deliverable, and no candidate evidence is invented); or NO CANDIDATE (the change proposed no code at all - a commissioning record, an investigation, a procedure finding: the record IS the deliverable, there is no diff or test to paste, and inventing candidate evidence would be a defect). Publication, when it happens, follows the workflow's stage 9 exactly - this file defines no publication procedure of its own; remote verification, when wanted, follows VERIFY.md's staging recipe (bundles - never a temporary shared branch).

End with three plain parts, always:
- **Your changes are here:** the full path of every file this change touched or created, plus the record file.
- **Where they stand:** stated from the ACTUAL outcome - either "your changes are saved in the project's history on this machine only; they leave this machine only when you push" or, after publication, "your changes are on the shared server as of <commit>; the team can see them" - and the push arithmetic (how many commits yours, how many upstream's, whether a pull comes first).
- **What to do next:** each open decision named with the recommended action and the exact command where one applies (e.g. `git push`), or the words "nothing further".

Who answers what at closeout: `.claude/DECISIONS.md`. Never suggest telling a user their bug is fixed unless the outcome is PUBLISHED.
