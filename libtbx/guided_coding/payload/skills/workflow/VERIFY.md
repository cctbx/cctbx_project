# The verification recipe

Why these rules exist: `.claude/RATIONALE.md`. Who answers what: `.claude/DECISIONS.md`.

Loaded by the Worker at the start of every verification (and for any remote run); the authoritative home of these rules. Subagents never need this file - their briefs carry what they need.

## Test conventions

- Tests are plain scripts named `tst_*.py`, run as `libtbx.python path/to/tst_name.py`.
- Use plain `assert`, and `libtbx.test_utils` helpers (`approx_equal`, `show_diff`) for numeric and text comparisons.
- A test ends by printing `OK` on success, matching the surrounding tests in the same directory.
- Small and explicit beats clever: one test file, direct assertions, no new test framework.

## Definitions

- NAMED BASELINE: the commit the approved plan names; subagents construct on it.
- CANDIDATE: the implementer's commit, parented on the named baseline.
- PINNED TEST: the test path plus its exact content (git blob id), fixed before implementation.
- BASELINE RUN commit and CANDIDATE RUN commit: the two commits actually executed. They are ALWAYS assembled so the approved test bytes sit on both code versions (see below) - even when the test path already existed, since the named baseline and the candidate need not contain the test-writer's additions. Each RUN commit is its base commit plus the pinned test file, built with the assembly recipe below - and before any run, verify with `git ls-tree` that the pinned test blob id is IDENTICAL in both RUN commits. The pin-stage demonstration (test fails before the fix) runs on the BASELINE RUN commit; the candidate does not need to exist yet.

The record states all of these, labeled. The NAMED BASELINE and the BASELINE RUN commit are different commits whenever the test is new; never call both "baseline" without the label.

## Command construction for approvals

Any command that will trigger an approval prompt is a single action - never a chain - presented under its four-line plain cover. Bookkeeping (setting variables, snapshots, logging) runs as separate commands that prompt for nothing. The recipes below are step lists to run one line at a time, not chains to paste whole.

## The executed test is always the approved bytes

The two run commits are ALWAYS assembled so that the approved test content - the exact blob the developer saw - sits on both code versions, whether the test file is new OR an extension of an existing file. Never assume an existing path's baseline or implementation commit contains the test-writer's additions: it need not. Before each decisive run, verify the executed test file's hash against the approved blob; a mismatch is an unexpected event, not a detail.

## Assembly recipe (adds the pinned test to a base commit without touching the working tree)

    export GIT_INDEX_FILE=<scratch>/tmp-index
    git read-tree <BASE>
    git update-index --add --cacheinfo <mode>,<blob of pinned test>,<path>
    TREE=$(git write-tree)
    git commit-tree $TREE -p <BASE> -m "assembly: pinned test onto <BASE> (recorded)"
    unset GIT_INDEX_FILE

`<mode>` is the file's real mode taken from the source tree (`git ls-tree` shows it), not a hardcoded value. Verify afterward: the new commit's parent is `<BASE>`; `git diff --name-only <BASE> <NEW>` lists exactly the pinned test; the blob id matches the pinned blob; `git status --porcelain` is unchanged.

## Verification procedure (live tree with save/restore)

The interpreter imports from this tree, so runs happen HERE, by checking out the RUN commit under test, never in a worktree. The Worker performs every step itself and records each command, its working directory, its exit status, and the relevant output, pasting results into its own message for the developer. A subagent's report of its own run is a claim, not the comparison.

0. **Exclusive use.** The developer's standing answer from stage 0 covers this change; do not re-ask it. If no standing answer was given, ask now, in the question shape: nothing else - no other session, no GUI job, no build - will use this tree until the restore completes. Do not start without it.
1. **Pure-Python guard.** `git diff --name-only` between the named baseline and the candidate, and between each RUN commit and its base: if any listed file does not end in `.py`, stop and return to the developer.
2. **Collision guard.** Neither RUN commit may track `.claude/`, `CLAUDE.local.md`, or any path that currently exists in the tree as an untracked or ignored file (checkout would overwrite it). Check with `git ls-tree -r --name-only` against the current untracked/ignored listing. Any collision: that local file is set aside (with the backup-and-ask step below) or the run stops.
2a. **LFS guard (repositories that route data files through git-lfs while the binary is absent).** `git status` and `git diff HEAD` cannot see damage to such files: git holds only the pointer. The instrument here is the POINTER-HASH CHECK - every LFS-pattern path's on-disk sha256 against the sha256 its pointer names - run before the first checkout and after the restore; a mismatch is an incident. And STOP before any checkout that would rewrite an LFS-pattern path: a checkout that must smudge such a path fails AFTER deleting the file from the working tree, which on a machine without git-lfs is unrecoverable. Confirm with `git diff --name-only` between the current tree and each RUN commit that no listed path matches an LFS pattern (`git check-attr filter -- <paths>`). Also: git-lfs installs HOOK scripts in `.git/hooks` (post-checkout and others) that call `git lfs` after every checkout and FAIL when the binary is off the shell's PATH - git then reports failure AFTER the checkout has completed, and a clone-based proof cannot see hooks. In such a repository every checkout and restore the round runs uses `-c core.hooksPath=/dev/null`, recorded as the reason; the exit status of a checkout is then meaningful again. In such a repository `git worktree add` fails outright, so the `implementer` and `test-writer` agents (which isolate by worktree) cannot start; dispatch `implementer-scratch` and `test-writer-scratch` instead, which create their own git worktree of the named baseline in the scratchpad with the LFS filters switched off for the command (`git -c filter.lfs.required=false -c filter.lfs.process= -c filter.lfs.clean=cat -c filter.lfs.smudge=cat -c core.hooksPath=/dev/null worktree add --detach ...`; data files stay as pointer text; hooks off because `worktree add` runs the post-checkout hook) and work there with absolute paths, under the same baseline and fingerprint checks. The Worker uses the same overrides for any git command that touches those worktrees.
3. **Record and prepare the tree.** Record `git rev-parse --abbrev-ref HEAD`, `git rev-parse HEAD`, and `git status --porcelain`. If `.claude/` or `CLAUDE.local.md` appears in the porcelain output, STOP - the exclude is missing and nothing here is safe. Then, one policy for what remains:
   - Untracked AND ignored files belong to the developer. Before any run, build the PROTECTED INVENTORY: every untracked and ignored FILE (not directory) from `git ls-files --others -z` and `git ls-files --others --ignored --exclude-standard -z`, EXCLUDING the procedure's own mutable areas (`.claude/records/`, `.claude/worktrees/`, and the scratchpad), which are evidence areas allowed to change. Record the developer's files and the procedure's own files as TWO SEPARATE inventories, never one list: a procedure package installed during the change makes procedure files change legitimately, and a combined inventory reports that as failing checksums on protected data - frightening, and false. For every inventoried file: record path and sha256 AND copy it to the scratchpad backup (recoverable bytes, not just a detector). If the inventory is large (many files or large size), stop and ask the developer how to proceed rather than backing up blindly. Status alone cannot see an overwritten file that keeps its name; a hash detects the loss, only the backup recovers it. For each untracked file: if it collides (step 2) it must be set aside; otherwise LEAVE IT IN PLACE, recorded. Before setting anything aside: copy it to the scratchpad, record its hash, and ask the developer in the question shape. Tests run from a scratch working directory outside the tree, so ordinary cwd-relative output cannot land among the developer's files.
   - Modified tracked files are stashed: record the content identity first (`git diff HEAD` saved to the scratchpad and hashed), then `git stash push -m "guided_coding-verify-CHANGEID"` for the tracked modifications only - NEVER a bare `-u`, which stashes every untracked file including those designated to stay in place; a file being set aside is copied to the scratchpad and removed explicitly, by path. The stash is retained until restoration is verified: restore with `git stash apply --index stash@{N}` (never `pop`, which deletes a successfully applied stash before the checks run), verify, and only then `git stash drop stash@{N}` by its identified entry. Record the stash entry as shown by `git stash list`.
   - "Clean enough to run" means: no modified tracked files, and every remaining untracked file recorded as left in place.
4. **Baseline run.** `git checkout <BASELINE RUN commit>` (detached, by hash). Import check: `libtbx.python -c "import MODULE; print(MODULE.__file__)"` for the touched module; the printed path must be inside this repository, or stop. List untracked files (snapshot A). Run the pinned test. Expected: it FAILS, for the reason the plan states; a failure for a different reason is not the decisive check - stop and classify.
5. **Contamination check.** List untracked files again (snapshot B). Anything the run created (B minus A) is removed or set aside and recorded BEFORE the candidate run. Because tests run from a scratch directory OUTSIDE the tree, each execution also gets a FRESH scratch output directory populated from the same declared inputs - a baseline-generated cache or result must never be reachable by the candidate run; any cache intentionally shared between runs is named in the record with the reason.
6. **Candidate run.** `git checkout <CANDIDATE RUN commit>` (detached). Verify the pinned test blob is identical to the baseline run's (compare `git ls-tree` blob ids). Repeat the import check. Run the pinned test (expected: PASS, ending in `OK`) and the regression checks the plan names. Repeat the contamination check. A pass is a test result with that test's limits; record it as such.
7. **Restore.** `git checkout` the recorded branch (or the original commit if it was detached). Find the stash entry BY ITS MESSAGE in `git stash list` and apply that exact entry with `git stash apply --index stash@{N}` - never a bare pop, never any pop before verification. Then verify restoration by CONTENT, not status alone: `git status --porcelain` matches the record; `git diff HEAD` hashes to the recorded value; every set-aside file is back and byte-identical to its scratchpad copy (`diff`); AND the protected inventory is recomputed and matches the pre-run inventory exactly - same paths, same hashes - so an overwritten leave-in-place file or a stray ignored output is caught by content, not by name; any mismatch triggers INCIDENT.md: preserve the current mismatching contents SEPARATELY from the pre-run backup, report the discrepancy, and perform only the recovery actions the Developer authorizes; retain the stash and backups until restoration is verified. Only after all four checks pass may the stash be dropped and may the scratchpad copies be considered redundant; keep them until `/wrap`.
## When a pinned test gains new material during a repair

A part added to the pinned test after review needs its own discrimination run against the code state it was written to catch - the PRE-REPAIR candidate, not the named baseline (where earlier parts fail first and the new part never executes). Without that run the new part is unfalsified machinery that has only ever been seen to pass. The recorded reason for changing a pinned test must include this discrimination evidence. Counterbalancing the discrimination run is judgment: one run suffices for a deterministic, disk-free path; record the choice either way.

8. **Counterbalance.** When the pinned test is newly written for this change, the decisive comparison runs four times, in this order: baseline, candidate, candidate, baseline. Both baseline runs must fail for the stated reason and both candidate runs must pass; any disagreement, or a failure that changes its reason, makes the result unclassified - stop and classify. A pinned test that already existed at the baseline may use the two-run comparison.
9. **Changed existing tests.** When the developer has approved changing an existing test's expectations, run BOTH the old and the new form of that test against BOTH code versions (four runs) and record all four transitions. This exposes a weakened expectation: the new form must fail on the old code for the stated reason, not merely pass on the new code.
10. **Record.** Every command, interpreter path, import-check output, exit status, and output excerpt goes into the change record before the result is presented.

**Interruption rule.** If any step is interrupted or ends in an ambiguous state, touch nothing further. Inspect the actual state (`git status --porcelain`, `git stash list`, `git rev-parse HEAD`), report it to the developer plainly, and proceed only once the state is understood. Never retry into an uninspected tree.

Checkouts use commit hashes (detached), never branch names, because a branch checked out in a construction worktree cannot be checked out here.

## The remote suite recipe (when the profile names a server)

ATTENDED USE ONLY until the shakedown - including its interruption drill - has passed and its record says so. Nothing here runs unattended before that.

- **Environment currency FIRST (prerequisite, not a tolerance).** Identify the intended PHENIX version and required repository/build state for this comparison. Compare the server installation against it BEFORE either run - EVERY module repository the suite touches, not only the changed one; report discrepancies and obtain the developer's approval for any update, performed by the normal PHENIX update/build procedure; verify the result; then FREEZE that environment across both the baseline and candidate runs - updating between them confounds the comparison and voids it.
- **Arrangement: the shadow installation.** `.claude/SHADOW.md` is the authoritative recipe for building a per-change workspace that the runtime actually imports, the swapped-set rule (the plan's repository scope), the two proofs required before use, and the limits. The profile records this site's commissioned arrangement.
- **One canonical path.** Workspace, shadow root and server lock live under one canonical PHYSICAL path (`pwd -P`, the form that appears in captured output and approval commands) recorded in the profile - a lock guarding a different path than the work is not exclusivity.
- **Dedicated test workspace, never the developer's working installation.** The candidate runs in a per-change workspace (`~/ch_runs/<change-id>/`), and the developer's personal tree is NOT modified - another job importing from it could see temporary code, and an interruption could strand it. The arrangement must pass BOTH executed proofs of SHADOW.md - import (the swapped module's `__file__` resolves inside the workspace) and harvest (the suite's module directory resolves to the shadow - for PHENIX print `libtbx.env.find_in_repositories('phenix')` alongside `phenix.__file__` under the workspace dispatcher, both inside the workspace - and a uniquely named dummy `tst_` file placed only in the workspace is harvested AND RUN by the suite, then is removed). A checkout alone proves nothing on this project's import model, and a fail/pass pair whose test exists in both trees cannot distinguish a mixed mode by itself. If the shakedown finds no workspace arrangement that passes the import proof, remote verification on that server is reported as unavailable and the developer decides - the personal-tree arrangement is not a silent fallback; it requires the developer's explicit, recorded election with the risks stated.
- **Execution boundary is the developer's explicit choice, recorded in the profile.** Remote commands run with the ssh account's full permissions; no local prompt or sandbox confines them. The profile states the chosen boundary: a restricted test account or server-side sandbox where available, or the developer's recorded acceptance that runs use the normal account with its exposure. Candidate code is treated as untrusted by default.
- **Staging.** The exact commit travels as a `git bundle` (scp) - never through the shared server, never as loose files. Publication is a separate, developer-authorized act; nothing in remote verification publishes anything.
- **Resources.** Use the server's scheduler if one exists; otherwise the profile sets the concurrency cap (nproc) and any memory limit as developer-approved values - a load glance is courtesy, not allocation. Quiet rule: proceed when fewer than 20 processes show >90% CPU (one-shot top, parsed); recheck every 10 minutes up to 2 hours, then ask the developer.
- **Locks and job identity.** Server lock by atomic `mkdir ~/ch_runs/.lock`, owner named inside, ownership confirmed before release. Prefer the server's scheduler job identity and its completion status where a scheduler exists. Otherwise a run is launched in its OWN SESSION (`setsid`) with a UNIQUE RUN TOKEN in its log path and working directory; the record holds the PGID, the token, the launch time, and the log path AT LAUNCH. "Still running" is a three-way question, decided in two passes. Pass 1: enumerate EVERY member of the recorded group - `ps -e -o pid,pgid,sid,etime,args` filtered by PGID ONLY (never also by token: a plain child such as `sleep 30` carries no token and would be missed). Pass 2, separately: look for ESCAPED descendants - processes whose arguments contain the run token, and processes whose actual working directory (`/proc/<pid>/cwd` where available, else `lsof`/`pwdx`) is inside the run's scratch directory; these are additional candidates for investigation, ownership established before any cancellation. Then classify, reading PASS 1 FIRST - a present terminal marker NEVER overrides a non-empty group (observed twice: a shell blocked waiting on an escaped descendant stayed in the group after the job wrote its end marker; a reader who consults the marker first concludes "finished cleanly" and retries into a live group). Group non-empty = still running, retry NOT safe, whatever the marker says; group empty and the log's terminal marker present = finished cleanly; group empty and marker absent = died or killed, retry only after diagnosis; candidates found but not attributable = UNKNOWN, treated as live. Every long remote job writes a terminal marker line at exit so the second and third cases are distinguishable. Stated limitation: none of this guarantees containment of arbitrary code - a descendant that changes group, discards the token, and leaves the directory is invisible to these checks. The commissioning drill tests a launcher whose child outlives it AND a descendant that changes group, and records plainly what the checks saw and did not see. After any disconnect, cancellation, or doubt: establish the group's state first - never retry, restore, release a lock, or clean a workspace over a possibly-live group; cancellation, when the developer authorizes it, is by group. The interruption drill must exercise a launcher whose child outlives it. Interruption handling follows INCIDENT.md, with the group check as its first inspect step.
- **Local-side helpers are macOS-checked.** The developer's machine lacks GNU `timeout` (bash 3.2, BSD userland): any local helper is verified to exist before use, and the working way to sever a connection for a drill is a backgrounded client plus `pkill` of that local ssh process.
- **Quoting.** The remote login shell is csh. Every remote command is ONE ssh argument wrapping bash: `ssh <host> "bash -lc '<command>'"` - verified once on the real server before first use; exit status captured with the output.
- **Rosters, not verdicts.** Record the roster even when a run is restricted to one test - confirm the filter selected exactly one test and name it, so an over-matching filter is caught rather than averaged. Record the full per-test roster both sides and compare AS ROSTERS: pass, fail (with mode - a both-sides failure whose mode changed belongs to the change), skipped (the suite's one real signal: a duplicate command), and MISSING - a test that produced no result line at all, which is also how a HUNG test surfaces, because the suite has no timeout mechanism and never emits a "timed out" outcome. A test that newly PASSES is explained exactly as one that newly fails: the old failure's cause, and evidence that the check still fails on a deliberately wrong value - a repair to a checker can hide more than it reveals. A test that is newly MISSING or newly skipped blocks exactly like a new failure; so does a run that did not finish, a suite that collected nothing, and a suite that did not run at all - a suite cannot pass by disappearing. Do not write a rule against "timed out": it cannot occur,. Absolute outcomes are recorded alongside transitions. The roster instrument's `needs_classification` list gates the result: a roster comparison is NOT clean while any command in that list is unclassified in the change's record, and classifying one means reading both tests in full - outcome, return code, attempts and the whole failure text, and for a replay conflict both copies in the log - never only the instrument's tuple; for a result with no failure text, only the log itself (for example captured standard output, where the run kept it) can say more. An empty `blocking` list says nothing was lost, not that every failure failed the same way. A classification may cite `.claude/records/known_failure_variation.md` - the machine-local list of tests whose failures are known to vary from run to run, each with its signature (the assertion or exception that stays the same, and what varies) - instead of re-reading the same texts every time; a test not on that list, or one whose text does not match its signature, is read in full. **Changes to the suite's own instruments** (its comparator, its harvester, this parser): "roster matches baseline" cannot be the gate, because the instrument is what changed. For such a change the gate is a pre-agreed, RECORDED acceptance standard written before the plan - what counts as an explained transition, what triggers the developer's decision, with count backstops - and the publication gate quotes that record. `phenix_regression/.claude/records/2026-09-14-check-results.agreed.md` is the worked example.
- **The suite here:** `phenix_regression.test_all_parallel nproc=<profile cap> sort`; every run gets its own log - `~/t96_<change-id>_<baseline|candidate>_<attempt>.log` - so baseline, candidate, and retries never share a file; PGID recorded at launch.
- **The installation the shadow links into.** Per SHADOW.md's protection section: the profile names it - a read-only execution environment, a disposable test installation (the practical default), or the working installation by explicit election with its exposure stated. After every remote run, record `git status --porcelain` in each linked module repository PLUS a sweep for ignored files written during the run - take the sweep's timestamp marker AFTER the before-pass completes, or exclude `.git/index`, because `git status` refreshes index files and the instrument otherwise reports its own before-pass as a change (`__pycache__`, `*.pyc`, and anything newer than the run's start time inside the linked module trees) - git status alone is blind to gitignored writes, which is exactly what a stray import leaves behind; set `PYTHONDONTWRITEBYTECODE=1` for every run that touches a linked tree. Under the working-installation election this remains detection, not prevention.
- **A fact is not a claim.** A fact about a run originates from the command you caused, the exit status the harness observed, and records written where candidate code cannot write. Output the candidate controls - a test's own captured stdout - is a CLAIM: displayed, never counted. Any number reported from a log carries its origin: the suite's own summary block (harness statement), a streaming result line (harness-formatted, candidate-triggered), or captured test output (claim). This is provenance, not a security control: a candidate that writes arbitrary bytes into the harness's own stream is beyond what any reader can distinguish, and the tooling says so rather than implying a guarantee.
- **Reading results.** The suite EXITS 0 WHILE REPORTING FAILURES, so process exit status is never a verdict - rosters are parsed from log content only. Every `bash -lc` command emits a stray PROFILE line from the login profile; strip it by pattern, never by dropping `-l`, which the environment needs. The suite requires an EMPTY working directory: each run gets a fresh empty directory inside the workspace with its log written OUTSIDE that directory.
- **A dead link is not a stopped job.** Severing the ssh connection never means the remote side stopped; remote processes may persist for minutes after. Establish remote state by the checks above, never by the state of the link.

## Files a refresh rewrites

When a round runs `libtbx.refresh` (or anything that regenerates files), the protected inventory captured BEFORE the round includes, by content, every ignored file the refresh is known to rewrite (version files, generated examples); after the restore each is compared by content and any that differ are copied back from the capture, with the regenerated copies kept as evidence. A file rewritten without a prior capture cannot be shown restored.

## The roster parser

Roster comparisons use `libtbx.test_utils.t96_roster` from the cctbx_project tree (`from libtbx.test_utils import t96_roster` under `libtbx.python`, from any repository); its registered test is `libtbx/tst_t96_roster.py`. The Worker records the parser file's sha256 beside every comparison. The procedure ships no copy of its own.

## Changes to untracked procedure files (other `.claude/` tools)

The live-tree recipe above assumes tracked files and `git diff`; the procedure's own tools are untracked and excluded from git. For a change to one of them: construction and verification run on COPIES in fresh scratch directories outside the tree, never on the installed files; identities are file hashes recorded before and after every round, not blob ids; the tree fingerprint of the installed `.claude/` files is taken before and after and must be unchanged; the tree lock is still held during any execution. The reviewer receives the two file versions and their hashes, not a `git diff`. The result is STAGED under `.claude/records/delivery-<change-id>/` with its hashes and shipped by the Guide in the next package revision; a Worker never installs it.

## Closeout preservation duties

Before deleting any subagent copy or branch: identify every commit the change record cites that is not reachable from master and pin each with a local tag under `guided_coding/<date>-<change>/` (tags made before the rename keep the `codinghelper/` prefix) - without this, garbage collection quietly rots the record's trail. Confirm at closeout: tags present, no scratch tst files, tree lock released, restores verified by content.

## The tree lock (one installation, one executor)

One interpreter, one live tree: two changes' code-executing phases must never overlap. Before ANY stage that executes code from the live tree - verification runs, regression checks, or a read-only reproduction - take the lock ATOMICALLY: `mkdir $PHENIX/.codinghelper_tree_in_use` - mkdir either creates it (you hold the lock) or fails because it exists (someone else does); check-then-create is not atomic and two sessions can both pass it. On success write owner.txt inside (change, session, date, stage). Before releasing, confirm owner.txt is yours, then remove the directory the moment the executing stage ends, and confirm removal at closeout. If it already exists: do not wait silently and do not proceed - tell the developer who holds it and what remains safe meanwhile (reading, planning, subagent construction without execution), and let the developer decide. The developer's standing exclusive-use answer from stage 0 covers everything outside the procedure; the lock answers the procedure's half. EACH round of runs is its own lock acquisition; the developer's standing answer is not re-asked unless it was given for a limited period or number of rounds that is now exhausted. No harvested or full-suite run happens while any subagent copy exists under .claude/worktrees/ - clean up first; the pre-harvest check below is what enforces it.

## Before any harvested or full-suite run

The regression suite harvests every `tst*` file anywhere under the module, so scratch copies become "registered" tests. Immediately before any harvested or full-suite run: `find .claude -name "tst*" -type f` from the repository top - it must return nothing; clean or defer if it does not. Keep this check even after the harvester itself excludes hidden directories.

All regression and full-suite results on this machine are before/after transitions, never absolute: some registered tests fail on macOS while all pass on Linux (recorded in CLAUDE.local.md), so a test failing at BOTH versions WITH THE SAME FAILURE MODE is a pre-existing platform failure - record it, do not chase it. Compare the failure modes, not just the verdicts: a both-sides failure whose mode CHANGED belongs to this change. Pass-to-fail transitions always belong to the change.

## Baseline conformance check (every subagent return, before anything else)

Subagents run concurrently from the same named starting code and are REQUIRED to construct on it; their first action is checking it out and confirming it. This check verifies that happened. On every subagent return, before using anything the subagent produced:

1. Record the subagent's actual base commit (its `git log` below its own commits).
2. If the base IS the named baseline: conformance holds; proceed.
3. If it is not, this is a RECOVERY situation, not a routine step. First inspect the subagent's FULL delta against its actual base - everything it changed, not only in-scope files - and its report for anything it read or relied on outside the in-scope files. Report to the developer in the question shape: what base it built on, how far from the named baseline, whether the in-scope files differ between the two, and what the subagent relied on. Only with the developer's word, transport the subagent's file(s) onto the named baseline with the assembly recipe (real file mode, subagent recorded as author, reason stated), and record that the subagent's reasoning was formed against a different base - identical in-scope bytes do not establish that its checks or assumptions applied to the named baseline. When in doubt, the safer repair is redispatching the subagent on the correct base.
